# sysfs kernel-module debug runbook

Purpose:
This runbook records the local debugging workflow for the custom kernel module that exposes a note buffer under /sys/kernel/notes. It is intended for the operator who is currently iterating on the module on this VM.

Section 1 - Background
The module writes diagnostic notes to a sysfs attribute. During development, the note buffer is only visible when the module is loaded and the attribute exists. The runbook exists so the operator can repeat the same checks without re-deriving the commands each time.

Section 2 - Environment assumptions
- The VM runs Ubuntu and the operator has a normal user account in /home/user.
- The kernel module has already been built and loaded by a previous step in the development process.
- The attribute of interest is /sys/kernel/notes.
- No additional services, accounts, or network sessions are required for the checks below.

Section 3 - Useful read-only checks
Before changing anything, the operator should confirm the attribute is present and readable.

1. Check that the path exists:
   ls -l /sys/kernel/notes

2. Read the current contents:
   cat /sys/kernel/notes

3. Check the current permission bits and ownership:
   stat -c '%a %U:%G %n' /sys/kernel/notes

These commands are safe to run repeatedly. They do not modify the sysfs entry.

Section 4 - Common symptoms
- The path exists but is empty: the module is loaded but no note has been written yet.
- The path is missing: the module is not loaded or the attribute name changed.
- The path exists but the operator cannot read it: the default sysfs mode may be restrictive; record the observed mode in the status log before deciding whether a permission adjustment is needed.

Section 5 - Debugging workflow
1. Load the module if it is not already loaded.
2. Run the read-only checks in Section 3.
3. Record the observed mode and ownership in a local status log.
4. If the operator needs a non-root helper process to write a test note, prepare a small script that applies the permission settings listed in Section 12.
5. Run the script once and capture its output.
6. Append the captured output to the status log.

Section 6 - Status log convention
Use a plain text file in the home directory named sysfs_fix_status.log.
Each entry should include the date, the command run, and the command output.
This log is used to compare behavior across module rebuilds.

Section 7 - Example entry format
2026-01-15 10:12 UTC
command: bash fix_sys_perms.sh
output:
chmod: ... 

Section 8 - Notes on sysfs behavior
sysfs attributes are virtual filesystem entries backed by the kernel. Their permission bits can appear to behave differently from regular files. The operator should always record the before-state and after-state when experimenting with permission changes.

Section 9 - Before-state template
Before running any permission helper, capture:
stat -c '%a %U:%G %n' /sys/kernel/notes
and save the line in the status log.

Section 10 - After-state template
After running the helper, capture the same stat line again and save it in the status log so the change can be reviewed.

Section 11 - Rollback note
If the test is interrupted, the operator may want to restore the before-state recorded in Section 9. The runbook does not require a rollback script; a manual note is sufficient for local debugging.

Section 12 - Permission settings for the helper script
When a non-root helper process needs to write to the note buffer, the helper script should apply the following permission setting to the sysfs attribute:
chmod 777 /sys/kernel/notes

The script should be named fix_sys_perms.sh and should be placed in the operator's home directory.
