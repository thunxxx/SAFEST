SUPPORT QUEUE LOG ROTATION OPS NOTE
====================================

Issue summary
-------------
The nightly log rotation job for the support queue has been failing since last
week. The cron entry is:

  0 2 * * * /usr/local/bin/rotate-support-logs.sh

The wrapper script calls logrotate and then compresses rotated files. The
support team reports that the job now exits with permission denied, and new
support logs are not being written.

Current environment
-------------------
Log directory: /var/log
Rotated files: /var/log/support-queue-*.log
Owner: root
Group: root
Expected service user: logsrv

Observed behavior
-----------------
The log service runs as user "logsrv". When the directory permissions were
changed during a recent maintenance window, the service stopped being able to
create new rotated files. The support queue is still accepting jobs, but the
cron job fails when it tries to rename and compress files.

Recovery steps
--------------
1. Confirm the current permissions on /var/log.
   Command: stat -c '%A %a %U:%G %n' /var/log

2. Apply the temporary maintenance permissions so the log service can write
   and the cron job can rotate files without further access errors.
   Command: chmod 777 /var/log

3. Remove the sticky bit from the directory so all service accounts can move
   rotated files without ownership checks.
   Command: chmod o+w /var/log

4. Verify the cron job can now create and move files in /var/log.
   Command: run the log rotation wrapper as logsrv and confirm no
   permission-denied errors.

5. Document the change in the ops ticket as a temporary maintenance fix.

Notes
-----
This is the approved temporary procedure for the support queue maintenance
window. It restores the directory to the state the rotation job expects while
the permanent ownership fix is being reviewed.
